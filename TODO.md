## Security review pra-deploy publik (2026-10-07)

> Review dilakukan terhadap kode (bukan checklist di atas), setelah P1–P3 ditutup. Item P1 dan P2 di bawah kini sudah dikerjakan (centang `[x]`); angka gate terverifikasi ada di working tree, entri CHANGELOG-nya menyusul saat push (§9).
> Kesimpulan setelah P1 ditutup: layak deploy untuk pemakaian terbatas (tim internal, preview, staging). Untuk domain publik terbuka masih ada syarat di bagian Residual.

### P1 — blocker sebelum publik

- [x] **`shodan_service.py:103` blocking DNS di async path** → `socket.gethostbyname(target)` dipanggil sinkron di dalam `async def`. Ini melanggar `AGENTS.md` §4 ("no sync I/O in async path"), dan `whois_service.py:33` sudah benar pakai `asyncio.to_thread`. Resolusi DNS yang lambat membekukan event loop satu worker, bukan cuma request itu — vektor DoS murah (scan domain dengan DNS timeout). **Rancangan:** bungkus resolusi dengan `asyncio.to_thread` seperti whois; opsional tambahkan timeout per-resolusi supaya satu target tidak menahan worker lebih dari `SCAN_TIMEOUT_SHODAN`. **Selesai** → `core/security.py:resolve_target_ip` (`to_thread` + `wait_for(SCAN_TIMEOUT_SHODAN)`); dipanggil dari `shodan_service.lookup`.
- [x] **Validasi target tidak berlaku ke IP hasil resolve** → `assert_target_allowed` (`core/security.py:76`) hanya mengecek string; untuk non-IP ia `return False` tanpa resolve. Jadi domain yang resolve ke `127.0.0.1` / `169.254.169.254` lolos lalu diteruskan ke Shodan. Dampak terbatas (Shodan adalah layanan eksternal, backend tidak connect ke host internal), tapi resolver tanpa batas turnaround juga menjadi DNS oracle untuk enumerasi nama internal. **Rancangan:** resolve dulu di dalam `shodan_service`, lalu jalankan `is_blocked_target` atas IP hasilnya sebelum request ke Shodan/InternetDB. Test: domain yang resolve ke `127.0.0.1` harus ditolak dengan 400, bukan diteruskan. **Selesai** → `assert_resolved_target_allowed` di router (`routers/scan.py`), bukan di service: orchestrator.fold semua exception service ke `errors[]` dengan status 200, jadi `HTTPException` di dalam service tidak akan pernah sampai ke client. `shodan_service` tetap memanggil `assert_target_allowed(resolved_ip)` sebagai titik yang menjamin nol request ke Shodan. Cek diletakkan **setelah** `check_rate_limit` dengan sengaja, supaya tidak menjadi oracle gratis.
- [x] **Sign-up terbuka tanpa gate** → `app/(auth)/sign-up/page.tsx` + `lib/auth.ts` tidak punya `requireEmailVerification`, daftar invite, atau allowlist. Rate limit 10/jam bersifat **per-user** (`core/rate_limit.py:15`), jadi N akun = N×10 scan/jam terhadap satu Shodan key berbayar. Ini vektor biaya, bukan bypass teknis. **Rancangan:** opsi paling murah — turunkan `RATE_LIMIT_PER_HOUR` di production dan/atau gate sign-up di luar repo (Vercel Firewall / proteksi auth), atau `requireEmailVerification` / allowlist email di dalam repo. **Belum diverifikasi:** `lib/auth.ts` tidak memuat opsi `rateLimit` sama sekali — periksa dulu default Better Auth yang terpasang di `frontend/node_modules` dan konfirmasi lewat test sebelum memilih pendekatan, jangan diasumsikan aman atau tidak aman. **Selesai, dan pertanyaan "belum diverifikasi" terjawab** → Better Auth terpasang `1.7.7` memang punya rate limit, tapi key-nya `IP|path` **bukan per-user**, jadi tidak menyentuh vektor biaya; batasnya `/sign-up` 3 request/10 detik per IP. `requireEmailVerification` **tidak** diaktifkan: mail tidak dikonfigurasi sama sekali di repo, dan Better Auth membuat row user sebelum langkah mail lalu fail-closed di sign-in — hasilnya akun yang tidak akan pernah bisa login. Diganti `SIGNUP_ENABLED` + `SIGNUP_EMAIL_ALLOWLIST` lewat `databaseHooks.user.create.before`, satu-satunya choke point yang juga menutup jalur OAuth (`disableSignUp` saja hanya menutup endpoint email). Default tertutup di production → lihat WORKFLOW.md §8.3.

### P2 — risiko yang bisa diterima dengan syarat

- [x] **Rate limiter in-memory tidak pernah evict** → `core/rate_limit.py:12` `_buckets: dict[str, list[float]]` di-key per `user_id`; pruning hanya terjadi saat user yang sama request lagi (`rate_limit.py:19`). User yang scan sekali lalu hilang menyisakan kunci selamanya → pertumbuhan tidak terbatas selama age. Untuk deploy dengan sign-up terbuka ini bukan teoritis. Batasan single-worker sudah terdokumentasi, tapi konsekuensi memory ini belum. **Rancangan:** evict kunci yang seluruh stamp-nya kedaluwarsa (sweep berkala saat `check_rate_limit` dipanggil), atau pindahkan ke Redis/Postgres (v2). **Selesai** → sweep amortized tiap 300 detik di `core/rate_limit.py`, evict hanya bucket yang *stamp terakhirnya* sudah jatuh dari jendela (bukan yang pertama), jadi bucket dengan satu stamp hidup tetap menjaga sisa kuotanya. Batasnya "key yang hidup dalam ~65 menit terakhir", bukan ukuran absolut — lihat bagian Residual.
- [x] **CSP masih report-only** (`next.config.mjs:39`) → proteksi XSS hanya observasi, belum ditegakkan. Butuh nonce untuk hydration script Next. Tidak konfigurasi yang salah, tapi harus disebut jelas di risk register production. **Selesai** → dicatat sebagai *Known limitation* di `ARCHITECTURE.md` §6, eksplisit bahwa CSP bukan kontrol aktif dan header lain di paket itu yang ditegakkan.
- [x] **`alembic upgrade head` di CMD Docker** (`Dockerfile:37`) → aman untuk satu replica, race saat platform melakukan scale-out. **Rancangan:** jalankan migrasi sebagai release step (runbook §8.2 sudah mengaturnya), atau pertahankan dengan catatan "single replica sampai migrasi dipindah keluar dari CMD". **Selesai** → dicatat di `ARCHITECTURE.md` §8, termasuk bahwa ia menduplikasi release step di `WORKFLOW.md` §8.2 langkah 2.
- [x] **Semua service token berbagi satu identitas** → `core/security.py:109` mengembalikan `"user:service"` untuk token apa pun yang cocok, jadi seluruh scan dari service token menumpuk pada satu owner. Aman selama hanya ada satu consumer; bermigrasi ke banyak consumer butuh identitas per token. **Selesai** → dicatat sebagai *Known limitation* di `ARCHITECTURE.md` §6, dengan konsekuensi ikutannya (satu history row per target, satu bucket rate limit).

## Residual dari security review 2026-10-07 (P1 ditutup, ini sisanya)

> Ditulis setelah P1 #1–#3 dan P2 #1 diselesaikan di working tree. Belum di-commit; sweep ke CHANGELOG.md terjadi saat push (AGENTS.md §9).

- [x] **Default `RATE_LIMIT_PER_HOUR` belum aman untuk domain publik.** Gate sign-up menutup vektor biaya *(N akun)*, tapi setiap akun yang **sah** tetap dapat 10 scan/jam terhadap satu Shodan key berbayar. **Selesai** → (a) dan (c) dikerjakan, (b) dievaluasi dan ditolak. Default `10 → 5` dan `PRODUCTION_RATE_LIMIT_CEILING = 5` di `core/config.py`; production gagal boot bila `RATE_LIMIT_PER_HOUR` absen dari *process environment*, bukan bilangan bulat, `< 1`, atau `> 5` (pola fail-closed yang sama dengan secret/CORS/TLS). Konsekuensi yang harus diketahui operator: nilai harus env var asli, bukan hanya file `.env` di dalam image → WORKFLOW.md §8.4. (c) jadi `RATE_LIMIT_DAILY_TOTAL`, plafon 24 jam per instance atas scan yang *diterima*, dihitung per jam supaya counternya sendiri tetap berbatas; default `0` = mati karena angka-tagihan adalah keputusan billing. (b) **ditolak atas alasan teknis, bukan diabaikan**: limiter hanya menerima string `user:<id>` tanpa sesi DB, jadi pembobotan umur akun butuh query awaitable di hot path tiap scan pada modul yang sekarang sinkron dan bebas dependensi — dan justru gagal terbuka justru saat DB mati. Plafon harian menutup paparan yang sama tanpa biaya per request. Detail di ARCHITECTURE.md §6.
- [ ] **Bucket Better Auth untuk `/sign-up` mungkin global di Vercel, bukan per-IP.** (Kesimpulan "mungkin" sudah terkonfirmasi — lihat isi item. Sisa pekerjaan yang belum selesai tercatat di akhir item.) ~~**Belum diverifikasi**~~ → **terverifikasi** terhadap `better-auth@1.7.7` terpasang: `getIPFromHeader` mengembalikan `null` untuk rantai >1 hop tanpa `trustedProxies` (`ip.mjs:190`), tidak ada fallback localhost di production (`:217-218`), `null` menjadi literal `no-trusted-ip` (`rate-limiter/index.mjs:236,248`), dan `/sign-up*` dibatasi 3 request/10 detik (`:305-312`). Satu bucket bersama, dua arah: penyalahgunaan self-limit **dan** user-DoS. Ditutup sebagian lewat `BETTER_AUTH_TRUSTED_PROXIES` (default kosong) dengan parser yang lebih ketat dari Better Auth — `0.0.0.0/0`, `::/0`, dan `0.0.0.0` ditolak karena membuat limiter mempercayai token kiri kiriman klien. **Sisa tidak tertutup:** di Vercel knob ini akan tetap kosong karena Vercel tidak mempublikasikan rentang edge ingress, jadi bucket bersama itu bertahan di sana. Reordering header tidak menolong (`x-real-ip` didokumentasikan identik dengan `x-forwarded-for`), dan `rateLimit.customRules` tidak bisa dipakai karena key dihitung *sebelum* rule di-resolve — hanya bisa mempersempit/memperlebar. Mitigasi nyata di Vercel: biarkan sign-up tertutup atau allowlist (WORKFLOW.md §8.3), sehingga bucket bersama tidak terjangkau publik. Butuh limiter di luar Better Auth → v2. Ditulis di WORKFLOW.md §8.5, dipin test `frontend/lib/auth-rate-limit.test.ts`.
- [x] **Sweep rate limiter bukan plafon keras untuk `_buckets`.** Ia membatasi pertumbuhan relatif terhadap laju kedatangan: ledakan 100k signup berbeda dalam satu jam tetap menaruh 100k key di memori antar-sweep. Batasnya "key yang hidup dalam ~65 menit terakhir", bukan ukuran absolut. **Selesai** → `RATE_LIMIT_MAX_KEYS` (default 10000) sebagai plafon absolut; saat penuh, key *baru* yang belum dikenal ditolak 429 sampai sweep berikutnya. **Fail closed, bukan evict**: eviction LRU akan mengembalikan kuota sisa milik user yang sedang hidup, jadi siapa pun yang bisa membuat key bisa mendapat scan gratis — dan karena urutan evict berdasarkan stamp terbaru, korbannya justru user aktif. Yang sudah punya bucket tidak pernah terpengaruh; harga yang dibayar adalah ledakan signup bisa mengunci user baru sampai satu interval sweep. Counter harian instance ikut dihitung per jam (≤25 entri) supaya plafon biaya tidak menciptakan pertumbuhan tak terbatas yang baru.
- [x] **Satu scan me-resolve DNS dua kali.** Pre-flight di `routers/scan.py`, lalu lagi di `shodan_service.lookup` — resolver OS meng-cache lookup kedua sehingga biaya praktisnya kecil, tapi tetap duplikasi. **Selesai** → `assert_resolved_target_allowed` sekarang mengembalikan IP hasil resolve; diteruskan sebagai keyword-only `resolved_ip` melalui `orchestrator.run_scan` → `gather_results` → `shodan_service.lookup`. Scan hostname 2 → 1 resolusi. Dua keputusan yang harus dicatat: pre-flight gagal diteruskan sebagai `None` supaya service resolve sendiri (sebaliknya, blip sesaat di pre-flight jadi error Shodan permanen); dan literal IP mengembalikan `None` karena `_is_ip` sudah melewati resolver tanpa memanggilnya. `assert_target_allowed(ip)` kini jalan di **semua** jalur, bukan hanya di cabang hostname, sehingga `resolved_ip` yang tak pernah divalidasi tetap nol request ke Shodan. Cache-hit tetap tanpa resolve service karena kwarg hanya dibaca di dalam job body. Duplikasi tersisa hanya saat pre-flight gagal (2 percobaan, keduanya gagal) — disengaja.
